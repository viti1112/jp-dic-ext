# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Manifest V3 browser extension ("KanjiFlow") that provides contextual Japanese dictionary lookups, built with WXT. The activation key (Shift/Alt/always-on) is user-configurable via `utils/settings.ts`, synced through `chrome.storage.sync` — plain hover with no modifier is ignored by default so the lookup pipeline doesn't fire on every incidental mouse movement. Implemented so far: the JMdict dictionary pipeline and IndexedDB store, the deinflection engine, longest-match cursor lookup, the content script/popup/messaging wiring, the AnkiConnect integration, a built-in mini-SRS (`utils/srs/`) as an alternative review backend with its own review-page entrypoint (`entrypoints/review/`), and the toolbar popup. The content-script popup's add-card button label and behavior follow `settings.reviewBackend` (`'anki'` or `'srs'`) - see `components/lookup-popup.ts`'s `AddCardOutcome`/`getButtonLabel`/`onAdd` and `entrypoints/content.ts`'s `addEntryViaAnki`/`addEntryViaSrs`. Still planned:

- `basicCardFromEntry()` hardcodes Anki's stock "Basic" model name; a model picker in the toolbar popup would need AnkiConnect's `modelNames`/`modelFieldNames` actions.
- The toolbar popup's brand "power" toggle from the original design mock was deliberately left unimplemented (no enable/disable-globally feature exists) rather than shipped as a decorative no-op button.

Known gap: the cursor-detection API (`document.caretRangeFromPoint`) is Chromium/WebKit-only, so the feature is a no-op on Firefox despite the `dev:firefox`/`build:firefox` scripts existing — see `entrypoints/content.ts`'s top-of-file comment before changing cursor detection.

## Commands

- `npm run dev` — start the WXT dev server for Chrome (hot-reloads the unpacked extension).
- `npm run dev:firefox` — same, targeting Firefox.
- `npm run build` / `npm run build:firefox` — production build, output in `.output/<target>/`.
- `npm run zip` / `npm run zip:firefox` — build and package into a distributable zip.
- `npm run compile` — type-check the whole project (`tsc --noEmit`) without emitting.
- `npm run test` — run the Vitest suite once (`*.test.ts` files next to the code they cover, e.g. `utils/deinflect/deinflect.test.ts`). These do **not** require `npm run build:dictionary` to have run first — `utils/dictionary/*.test.ts` seed a tiny hand-written fixture dictionary into `fake-indexeddb` rather than touching the real ~219k-entry JSON, so the suite stays fast and runs on a fresh clone.

- `npm run build:dictionary` — regenerate `public/dictionary/jmdict-en.json` (and `data/pos-tags.json`) from the raw JMdict XML. Requires `data/raw/JMdict_e` to exist first: download it from `http://ftp.edrdg.org/pub/Nihongo/JMdict_e.gz` (EDRDG, open licence — attribution still needed in the README once published) and `gunzip` it into `data/raw/`. Both `data/` and `public/dictionary/` are gitignored — they're regenerated from source, not committed, because the parsed dictionary alone is ~40 MB. **On a fresh clone, run this before `npm run compile`/`dev`/`build`**: WXT's `getURL()` typing (`PublicPath`) is generated from whatever actually exists under `public/` at `wxt prepare` time, so referencing `/dictionary/jmdict-en.json` type-checks only after the file exists and `wxt prepare` (or `npx wxt prepare` directly) has re-run.

## Architecture

This is a [WXT](https://wxt.dev) project (Vite-based MV3 framework, file-based entrypoints similar to Nuxt/Next).

- **`entrypoints/`** — one file/folder per extension surface; WXT derives the manifest's `background`, `content_scripts`, and `action.default_popup` from what it finds here (`background.ts`, `content.ts`, `popup/`). Adding a new entrypoint (e.g. a dedicated options page, as opposed to this toolbar-click popup) means adding a new file/folder here, not hand-editing the manifest. `popup/` is the toolbar-icon dropdown: activation-mode picker, a Anki/mini-SRS `reviewBackend` toggle, AnkiConnect status/deck name (shown only in Anki mode), a due-card count + "start review" button (shown only in mini-SRS mode), dictionary entry count, and the recent-additions log - backed by `utils/settings.ts`/`utils/anki.ts`/`utils/anki-log.ts` directly, and by `utils/messaging.ts`'s `requestDictionaryCount()`/`requestDueSrsCount()` for the two counts (asks the background, which already holds the seeded IndexedDB connections open, rather than opening its own - the same background-owns-the-DB pattern `lookup`/`addToAnki` already follow). `review/` is a standalone page (not manifest-derived the way `popup/`'s `action.default_popup` is - opened via `browser.tabs.create({url: browser.runtime.getURL('/review.html')})` from the toolbar popup) that reviews due mini-SRS cards one at a time via `requestDueSrsCards()`/`requestReviewSrsCard()`; it re-fetches another batch once the current one empties, since a card's `dueAt` always moves into the future on review so a re-fetch can never return the same card twice.
- **`wxt.config.ts`** — the single source of truth for `manifest.json` fields that aren't derived from entrypoints (name, `permissions`, `host_permissions`). AnkiConnect access is granted here via `host_permissions: ['http://127.0.0.1:8765/*']`; new cross-origin calls need their origin added here, not just in `fetch()` calls.
- **`components/`** — shared UI/non-entrypoint pieces: `lookup-popup.ts`'s `LookupPopup` class, a Shadow-DOM-isolated card the content script shows/hides/repositions per lookup (created once per injection, not recreated per hover). Starts `pointer-events: none` (passive, never blocks page clicks); `pin()` switches it to interactive and freezes it (`show()`/`hide()` become no-ops) so its per-entry add-card button is clickable without the next `mousemove` tick replacing its content — `unpin()` (wired to Escape in `entrypoints/content.ts`) reverses both. The button's label and click handler are backend-agnostic (`AddCardOutcome`, constructor args `getButtonLabel`/`onAdd`) - `entrypoints/content.ts` decides whether a click feeds Anki or the mini-SRS.
- **`utils/content/`** — DOM logic the content script needs that isn't itself an entrypoint: `text-run.ts`'s `extractTextRun()`/`isInsideRubyText()` pull the text run at a `caretRangeFromPoint` result and skip `<rt>` (furigana) nodes; tested with jsdom (`// @vitest-environment jsdom` in its `.test.ts`) since it's DOM-shaped but doesn't need a real browser.
- **`utils/messaging.ts`** — the typed `browser.runtime.sendMessage`/`onMessage` contract between content script/popup and background: `ExtensionMessage` is a discriminated union (`lookup`, `addToAnki`, `getDictionaryCount`, `addToSrs`, `getDueSrsCount`, `getDueSrsCards`, `reviewSrsCard`) and `registerMessageHandlers()` dispatches on `message.type` against a `MessageHandlers` map, so adding a message type is additive — a new union member, a new `MessageHandlers` field, a new `switch` case — not a rewrite of this function (all four SRS types were added this way). Every `switch` case must call `sendResponse` on *both* its `.then` and `.catch` path - skipping it on failure (as `addToSrs` once did) leaves the sender's `sendMessage` promise permanently unsettled instead of rejecting or resolving, which hangs the caller forever rather than surfacing an error.
- **`utils/anki.ts`** — `addNoteToAnki()` posts to the local AnkiConnect REST API. Its result type distinguishes "AnkiConnect never answered" (`reason: 'unreachable'` — Anki not running *or* its `webCorsOriginList` doesn't include this extension's origin; `fetch()` can't tell those two apart) from "AnkiConnect answered with a logical error" (`reason: 'rejected'`, e.g. bad deck name). `basicCardFromEntry()` maps a `DictionaryEntry` onto Anki's stock "Basic" note type (Front/Back), built from `utils/dictionary/display.ts`'s `entryDisplayFields()`. `pingAnkiConnect()` is the toolbar popup's connectivity check.
- **`utils/anki-log.ts`** — a capped (20-entry), most-recent-first list of successfully-added terms in `chrome.storage.local`, appended to from `entrypoints/background.ts` right after a successful `addNoteToAnki()` and read by the toolbar popup to render "Добавлено в Anki".
- **`utils/settings.ts`** — `ExtensionSettings` (`activationMode`, `deckName`, `reviewBackend`) in `chrome.storage.sync`, so it follows the user across devices; `onSettingsChanged()` lets the content script react live to the toolbar popup editing settings without a reload. `isActivationHeld(mode, event)` is the one place that maps a mode to a modifier-key check - the content script never inspects `event.shiftKey`/`event.altKey` directly.
- **`utils/dictionary/`** — shared dictionary logic used at both build time and runtime: `types.ts` has the canonical `DictionaryEntry`/`Sense` shape, `frequency.ts` ranks competing entries that share a surface form (e.g. 橋/箸/端 all read はし) using JMdict's own `priority` tags — see the doc comment there for why this doesn't reorder senses within one entry. `display.ts`'s `entryDisplayFields()` picks the headword/reading/glosses to show for an entry - the one place both `utils/anki.ts` and the mini-SRS path (`entrypoints/content.ts`) and the content-script popup (`components/lookup-popup.ts`) derive that from, so the three stay consistent. `db.ts` is the IndexedDB layer (`openDictionaryDB`/`seedIfEmpty`/`lookupExact`, indexed by kanji and reading, both multi-entry). `lookup.ts`'s `lookupAtCursor()` is the entry point everything else builds toward: longest-match substring scan from a cursor position, combined with `utils/deinflect/`'s candidates and frequency ranking.
- **`utils/srs/`** — the built-in mini-SRS, a from-scratch SM-2 (SuperMemo 2) implementation in its own IndexedDB database (`jp-dic-ext-srs`, separate from the dictionary's - different lifecycle: small, user-generated, mutable). `types.ts` has `SrsCard`/`NewSrsCard` (a self-contained snapshot, not a live join to the dictionary) and the four-button `ReviewQuality`. `scheduler.ts`'s `reviewCard()` is the pure, generic (works on both `NewSrsCard` and `SrsCard`) SM-2 scoring function - see its doc comment for the algorithm's reference behavior. `db.ts`'s `reviewCardById()` reads, scores, and writes a card within a single IndexedDB transaction specifically so two concurrent reviews of the same card can't lose one's update (a separate get-then-put across two transactions would race).
- **`utils/deinflect/`** — the Japanese deinflection engine (verbs + i-adjectives). `rules.ts` is table-driven per conjugation class (`godanRules()`/`suruRules()`/`ichidanShapedRules()` generators, not hand-copied per class) and documents its own known gaps at the top of the file. `deinflect.ts`'s `deinflect(word)` recursively strips suffixes and returns candidates tagged with the part-of-speech the real dictionary entry must have; `tagsMatch()` is the one place that checks a candidate's tags against real JMdict tags (it knows about the `"any"` sentinel on the unmodified input, so callers don't have to).
- WXT auto-imports its own globals (`defineBackground`, `defineContentScript`, `browser`) inside `entrypoints/` — no explicit import needed, see `.wxt/types` after `wxt prepare` (runs automatically via the `postinstall` script) if a global's type isn't resolving.
- Manifest target defaults to `chrome-mv3`; `-b firefox` flags switch the build target without touching source files.
- **`scripts/jmdict/`** — the JMdict XML → JSON build pipeline, run with `npm run build:dictionary` (not part of the extension bundle itself; imports the shared `DictionaryEntry` type from `utils/dictionary/types.ts`). The one subtlety: JMdict's DTD declares entities like `&v5m;` that expand to a long English description ("Godan verb with 'mu' ending"), but the deinflection engine (planned) needs the short code itself to validate conjugation classes — so `parse-jmdict.ts` resolves each entity to its own name (`v5m`), not its declared value, and separately dumps the code→description map to `data/pos-tags.json` for any future human-readable display.
